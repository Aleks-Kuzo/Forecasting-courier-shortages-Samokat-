# Прогнозирование дефицита курьеров (тестовое задание, Самокат)

Тестовое задание Data Science для Самоката. Задача — спрогнозировать **дефицит курьеров** (`target`) для каждого даркстора на неделю вперёд (24 ноября 2025 г.) на основе исторических данных о фактической и прогнозной нагрузке.

## 🎯 Задача

По историческим данным о работе дарксторов (фактическая нагрузка, прогнозы, число курьеров, маркетинговые расходы и др.) предсказать, скольких курьеров не хватит для обслуживания заказов на предстоящей неделе — задача регрессии, метрика качества **WAPE** (Weighted Absolute Percentage Error).

## 📊 Данные

Проект использует три исходных источника, объединяемых по ключам `calendar_dt` (дата) и `store_id` (даркстор):

- **`facts.csv`** — фактические показатели за предыдущую неделю: число курьеров, необходимое для обслуживания заказов, фактическая нагрузка, число доступных и вышедших на смены курьеров, процент опозданий, лайфтайм даркстора, город, отток курьеров, признак повышенного спроса, затраты на маркетинг.
- **`shifts_prediction.csv`** — прогноз на неделю вперёд: предсказанное число заказов, предсказанная нагрузка на курьера, предсказанное необходимое число курьеров.
- **`train.csv` / `test.csv`** — целевая переменная `target` (дефицит курьеров) по датам и дарксторам; `test.csv` содержит дарксторы, для которых нужно построить прогноз на 24.11.2025.

## 🔧 Пайплайн

1. **Объединение данных** — `train`/`test` склеиваются в один датафрейм и обогащаются признаками из `facts` и `shifts_prediction` по ключам дата + даркстор.
2. **Обработка пропусков**:
   - Для признаков с небольшим числом пропусков — заполнение **локальной медианой** (по конкретному даркстору), а где это невозможно — медианой по всей выборке.
   - `marketing_costs_lag_1` — пропуски заполняются нулём.
   - `fact_percent_lateness_lag_1` — сохраняется отдельный бинарный флаг `lateness_missing`, а сами пропуски заполняются значением `-1` (модель должна отличать "опозданий не было" от "данных нет").
3. **Feature Engineering**:
   - Календарные признаки: месяц, номер недели.
   - **Дельты** между прогнозными и фактическими значениями (абсолютные и в процентах) — по числу курьеров, числу заказов и нагрузке.
   - **Лаги на 2 недели** по ключевым метрикам (заказы, штат, нагрузка, опоздания).
   - **Скользящее среднее** (окно 3 недели) по тем же метрикам.
   - Категориальный признак `city_nm`.
4. **Валидация и обучение** — **K-Fold (5 фолдов)** на **LightGBM Regressor** (objective/metric — MAE), с ранней остановкой по валидации; предсказания усредняются по фолдам.
5. **Постобработка** — обрезка отрицательных предсказаний (`clip(0, None)`), округление до целого числа курьеров.

## 📈 Модель и метрика

- **Модель:** `LGBMRegressor` (LightGBM), 1500 деревьев, `learning_rate=0.03`, `num_leaves=22`, `max_depth=5`.
- **Кросс-валидация:** `KFold(n_splits=5, shuffle=True, random_state=42)`.
- **Метрика:** WAPE (Weighted Absolute Percentage Error) — считается на каждом фолде, финальный результат — среднее по фолдам (значение выводится при запуске ноутбука).

> Примечание автора: изначально признаки готовились под CatBoost, но по факту LightGBM показал результат лучше; переход на K-Fold валидацию дополнительно улучшил метрику.

## 💡 Возможные направления развития

- Попробовать таргет-энкодинг или более тонкую обработку `city_nm` вместо простого category-типа.
- Добавить кросс-валидацию по времени (time-based split), а не случайный K-Fold, чтобы точнее оценить качество на будущих неделях.
- Провести полноценный подбор гиперпараметров (Optuna) вместо ручного перебора.
- Добавить блендинг/стекинг с CatBoost, который использовался на более ранней стадии.
- Проверить важность признаков (feature importance / SHAP) для интерпретации модели.
